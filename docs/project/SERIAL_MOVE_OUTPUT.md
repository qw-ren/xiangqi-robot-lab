# 完整网页的走棋串口输出

本次直接修改现有项目，没有新建项目副本。完整网页、虚拟下棋、AI 分析、棋谱/FEN、图像输入、相机、网络相机、ArUco 与原定位后端、视觉观测接口、日志和独立策略程序均保留。视觉源码、模型与视觉配置没有改动。

本机不再导入 `Arm_Lib`、读写实机关节或通过 GPIO 操作电磁铁；网页旧 TCP 运动/归零入口已停用。`dofbot.py`、`DofbotController` 及 `/api/dofbot/...` 的旧名称保留用于兼容现有代码，实体后端的含义改为“走棋串口输出”。原有纯软件动作预演仍可在 mock 中使用。

## 如何启动

使用原来的 Python 环境，安装新增的串口依赖：

```text
python -m pip install pyserial==3.5
```

在项目根目录启动完整网页。引擎路径替换成自己已部署的真实可执行文件，下面的 `COM3` 也要替换为实际串口：

```text
python run_local.py --engine "引擎的完整路径" --nnue engine_assets/pikafish.nnue --serial COM3 --baud 115200
```

树莓派示例（已经准备好可执行的 Linux ARM Pikafish）：

```bash
python run_local.py --engine engine_assets/pikafish --nnue engine_assets/pikafish.nnue --serial /dev/ttyUSB0 --baud 115200 --host 0.0.0.0 --camera
```

原有 `--vision-backend`、`--aruco-config`、`--board-orientation`、`--vision-only` 等视觉参数原样保留，请继续使用队友已验证的配置。`--vision-only` 仍然只允许视觉预览，不开启走棋。现有 ArUco 的 `preview_only` 保护未改动，原始观测不会因此被自动当作已确认棋局。

也可以不传 `--serial`，进入网页后在“走棋串口与离线预演”中填写串口和波特率，点击“连接串口／模拟器”。空白串口且未配置 serial 后端时，连接的是原有离线模拟器，不会发送串口。不能在对局中途更换输出端口。

网页地址仍是 `http://127.0.0.1:5000/`，端口仍可用 `--port` 修改。已有服务必须先正常停止再重新启动，才能加载此次改动；浏览器刷新后会加载新版扩展脚本。

## 网页、决策与串口如何同步

```text
现有视觉/虚拟棋盘输入 → 现有 Pikafish bestmove
 → game_logic.apply_ai_best_move
 → dofbot.apply_move（只校验一次）
 → 串口写入同一步 MOVE → 同一份结果更新网页棋盘/FEN/棋谱
```

- 连接 serial 后，模拟对局的 AI 决策也会同步发送；想做完全离线测试时使用 mock，且不要连接真实串口。
- 发送的是 AI 的实际 `bestmove`，没有再次调用引擎生成另一走法。玩家手动或视觉识别的走法不作为 AI 指令发送。
- 串口失败或短写时不提交网页落子，并显示错误；不自动重新搜索、重新连接或重复发送。异常可能发生在部分数据已发出之后，应核对下位机接收情况，结束本局并检查棋盘，再重新开局。
- “已写入串口”不表示“机械臂已执行”。串口消息里的全盘是本步走完后的**预期**棋位。
- 串口实体对局若使用实时 camera/network 输入，保留原有连续三次稳定、全部棋子完全一致的视觉核对。网页先显示决策结果，核对通过后才解除等待；不会再追加第二次相同走法。不使用实时视觉的虚拟对局不会等待实体确认。
- 下位机需自行解释如何抓放、吃子、标定、控制舵机和末端工具。本程序不发送这些动作细节，也不接收执行 ACK。点击“停止后续输出”只结束本机后续输出，不会撤回已经发送的消息。

## 下位机接收格式

串口参数为双方一致的波特率（默认 115200）、8 数据位、无校验、1 停止位。每条消息是 **ASCII 编码的一行 JSON，以 LF (`\n`) 结尾**；没有 CRC 外壳。接收方应累积到换行再解析，不能假设一次串口读取就是完整消息。

`b2e2` 的结构示例（为便于阅读省略了两个 FEN 和全盘列表的具体值；实际消息会完整发送）：

```json
{
  "type": "MOVE",
  "command_id": "对局编号:0:b2e2",
  "game_id": "对局编号",
  "ply": 0,
  "move": "b2e2",
  "from": {"row": 7, "col": 1},
  "to": {"row": 7, "col": 4},
  "piece": "C",
  "capture": null,
  "before_fen": "完整的走前FEN",
  "expected_fen": "完整的走后预期FEN",
  "pieces": [{"piece": "C", "row": 7, "col": 4}]
}
```

实际 `pieces` 包含**全部存活棋子**，不止示例中的一个。`piece` 大写为红方、小写为黑方，使用 K/A/B/N/R/C/P。`capture` 是被吃棋子的编码，无吃子则为 `null`。

`row` 从黑方底线 0 到红方底线 9，`col` 从左到右 0..8；`from`/`to` 使用明确的 row/col 对象。ICCS 的数字方向相反，关系为 `row = 9 - ICCS数字`，所以 `b2e2` 对应第 7 行第 1 列到第 7 行第 4 列。

`game_id` 每次开局变化；`ply` 是 AI 走前的半步数；`command_id` 标识本局本步。下位机应按 `command_id` 去重，不应把收到重复消息解释为再次搬运。不要将新 Web 的 MOVE 消息与独立 `xiangqi_strategy` 原有的 CRC/RPC 协议混用；独立策略程序未改动，也不要让两个进程抢占同一串口。
